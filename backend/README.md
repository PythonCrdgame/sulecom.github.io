# SulE-Com backend deployment

The frontend is static HTML, but signup/sign-in and protected marketplace actions require the Express API in this directory. A static-only deployment (including the current Vercel route) cannot run this backend. Deploy this repository as a **Render Web Service** using the included `render.yaml`, or use another Node host that can run a persistent Express process and mount persistent storage.

## Render setup

1. In Render, create a Blueprint from this repository and approve the `sulecom` web service described by `render.yaml`.
2. The service root is `backend`; Render installs dependencies and starts `node server.js` from there.
3. The included persistent disk stores the SQLite account database and session store. Do not remove the disk or change its mount path without backing up/migrating those files.
4. Use the resulting Render URL to test `/api/health`, `/signup`, and `/signin`. Serve the app only over HTTPS in production.
5. The old Vercel config continues to serve static files only. Point customers to the Render service URL (or configure a same-origin reverse proxy to it); don't expect `/api/*` to work on a static Vercel deployment.

`SESSION_SECRET` is generated by Render. For another production host, set `NODE_ENV=production`, set a long random `SESSION_SECRET` in its secrets manager, configure `DATABASE_PATH` and `SESSION_DIR` on a persistent disk, and set `TRUST_PROXY=true` only when the service is behind a trusted reverse proxy. The server fails at startup in production if the session secret is missing. For local development, run `cd backend && npm install && npm start`; its local-only fallback secret is not suitable for deployment.

## Authentication included

- bcrypt password hashing; input validation; normalized email; duplicate account handling
- server-side, SQLite-persisted sessions; HttpOnly, SameSite=Lax cookies, Secure cookies under HTTPS; session ID rotation on login/signup; logout invalidation
- rate-limited signup/sign-in; authenticated product creation, order submission, and role check from the database
- public user-directory endpoint removed; old seeded `seller@sulecom.local` / `seller123` demo account removed during startup

## Verify after deployment

- Signup a new account with a 12+ character password; duplicate signup should return 409.
- Sign in with a wrong password and confirm a generic 401; then sign in correctly and verify `/api/session` returns the user.
- Restart the service and verify the session remains valid; log out and confirm `/api/session` returns 401.
- A guest should receive 401 from product creation and order submission; a buyer-only account should receive 403 when publishing.
- `/api/users` should not return a user list.

The database-backed sessions and SQLite database need persistent storage. Before accepting real orders, the order API should also derive totals from trusted product records rather than trusting prices/totals sent by the browser; this deployment/auth change does not implement payment processing, email verification, or password reset.
